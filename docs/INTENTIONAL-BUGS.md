# 刻意留給學生的 bug 清單（簡報製作用）

> 這份文件給**寫課堂簡報的人或 AI**（例如 ChatGPT）讀。
> 它列出 GYOZA WOOD 鍋貼店遊戲裡**故意挖好、要學生在課堂上找出來並讓 AI 修好的地方**。
> 遊戲規則以 `docs/RULES.md` 為準；程式表現跟規則書不一樣的地方，就是這裡列的 bug。
> 最後更新：2026-10-02

---

## 0. 給寫簡報的 AI：先讀這段

### 課程背景

- **對象**：完全沒有程式基礎的上班族、法律系與土木系學生，目標是學會在工作上用 AI。
- **課程重點不是做遊戲。** 遊戲只是讓課程好玩的外殼，學生真正要學的是：
  1. 怎麼寫 **Skill**（給 AI 的工作說明書）
  2. 怎麼串 **MCP**（讓 AI 能操作瀏覽器等外部工具）
  3. 怎麼做自己的 **AI Agent**（會自己用工具、照說明書做事的助手）
- **開發環境**：VS Code + Claude Code。學生不自己寫程式，而是**描述問題、讓 AI 修、驗收 AI 的成果**。
- **時數**：12 小時，分 3 天，每天 4 小時。

### 這些 bug 的設計原則

| 原則 | 說明 |
|---|---|
| 開局就能玩 | bug 不會讓遊戲壞掉，只會讓遊戲「掉漆」：數字怪怪的、功能沒反應 |
| 學生自己發現 | 先玩遊戲、對照規則書找怪事，再用 `npm run check` 印證，動機來自學生自己 |
| 一個檔一條規則 | 每個 bug 都在 `web-lab/src/game/rules/` 裡的一個獨立檔案，AI 修改範圍很小、好檢查 |
| 有客觀驗收 | `npm run check` 會逐條印出 PASS／FAIL，修好前後的數字可以直接放進簡報 |
| 全班一樣 | 遊戲沒有亂數，同樣的操作一定得到同樣的數字，老師可以在台上示範、全班一起核對 |

### 寫簡報時請遵守

- 用**繁體中文**、口語、友善，多用鍋貼店和遊戲的比喻。
- 每個 bug 的簡報流程建議：**玩遊戲看到怪事 → 小試身手：哪裡怪？ → 對照規則書 → 讓 AI 修 → `npm run check` 驗收 → 看 diff → commit**。
- 學生不寫程式碼，簡報裡**不要要求學生自己打程式**；要教的是「怎麼跟 AI 描述問題」和「怎麼驗收」。
- 本文件第 3 節有每個 bug 的**正確寫法**，那是給老師核對用的；簡報裡要不要放，由老師決定。

## 3. 每個 bug 的詳細說明

### bug 1：成交規則（超賣）

| 項目 | 內容 |
|---|---|
| 檔案 | `web-lab/src/game/rules/sales.js`，函式 `tryBuy` |
| 規則書 | 「客人怎麼決定買不買」：買得到要同時符合**有上架、還有貨、買得起**三個條件 |
| 掉漆版 | 只檢查「有上架」和「買得起」，**沒檢查還有沒有貨** |
| 學生看到的怪事 | 客人包選「預設路人」，只上架招牌鍋貼 5 份、70 元，營業收入是 **700 元**（賣了 10 份），不是 350 元；也從來沒有客人說「賣完了」 |
| 怎麼發現 | 「我只備 5 份，怎麼賣出 10 份？」 |
| 修好後 | 營業收入 350 元，第 6～10 位想買招牌的客人買不到，卡片顯示「賣完了」 |
| 驗收 | 成交規則 3／6 → 6／6；`playtest` 案例 T1 |
| 換關版本 | 修好的版本是 `checkpoint-1` |
| 正確寫法 | 在「太貴」的檢查**之前**加上：`if (stockLeft <= 0) return { ok: false, reason: 'sold_out' };` |
| 教學重點 | 第一次讓 AI 改程式：用自己的話描述問題、看 AI 改了什麼（Source Control 的 diff）、commit 存檔 |
| 連鎖影響 | 這個 bug 沒修，「倉庫盤點」頁會出現「備貨 5、賣出 10」，任務 2「沒有客人因為賣完而沒買到」也永遠判不準 |

### bug 2：收支規則（大家都很有錢）

| 項目 | 內容 |
|---|---|
| 檔案 | `web-lab/src/game/rules/money.js`，函式 `wasteFee`、`dailyProfit` |
| 規則書 | 「收支與廚餘清潔費」：淨利＝營業收入 − 備貨成本 − 宣傳費 − 廚餘清潔費；清潔費是階梯式（0～5 份免費、超過 5 份每份 3 元、超過 15 份另加 50 元） |
| 掉漆版 | `wasteFee` 永遠回傳 0；`dailyProfit` 直接回傳營業收入，什麼都沒扣 |
| 學生看到的怪事 | 報廢再多清潔費都是 0 元；當日淨利＝營業收入；隨便玩五天都有一萬多元 |
| 怎麼發現 | 「我怎麼這麼有錢？跟同學比一下」「報廢 20 份，規則書說清潔費應該是多少？」 |
| 修好後 | 報廢 20 份收 95 元（(20 − 5) × 3 + 50）；範例策略（四樣各 10 份、原價、不宣傳）五天後只剩 3,806 元 |
| 驗收 | 收支規則 2／8 → 8／8；`playtest` 案例 T2、T3 |
| 換關版本 | 修好的版本是 `checkpoint-2`（第 1 天結束的進度） |
| 正確寫法 | `wasteFee`：照階梯計算；`dailyProfit`：`return revenue - stockCost - promoCost - wasteFee;` |
| 教學重點 | 第一次用 `change-feature` Skill：AI 先寫計畫 → 人核准 → AI 修改 → 跑 check → 用固定格式回報 |
| 數字對照 | 同一套玩法，學生版 11,935 元 → 修好後 3,806 元（官方客人包、範例策略 `plans/example-even.json`） |

### bug 3：口碑規則（星等不會動）

| 項目 | 內容 |
|---|---|
| 檔案 | `web-lab/src/game/rules/reputation.js`，函式 `updateStars` |
| 規則書 | 「來客數與口碑星等」：每天打烊看進店客人的滿意比例，以 0.5 顆為單位升降，每天最多動 1 顆，範圍 1～5 顆 |
| 掉漆版 | 永遠回傳原本的星等（3 顆） |
| 學生看到的怪事 | 怎麼經營星等都是 3 顆；**定價全部訂最高還是賣得出去**，因為客人不滿意也沒有後果 |
| 怎麼發現 | 「你的星等有變過嗎？」「定價高過參考價，客人會不滿意，但規則書說不滿意會怎樣？」 |
| 修好後 | 以官方客人包、每天備招牌 20、玉米 15、紅茶 15、豆漿 15 份為例：全部定最高價，第 1 天星等 3→2、第 2 天 2→1，第 3 天錢不夠進貨（等於倒店）；全部定參考價，五天後 5,179 元。學生版裡這兩種定價分別是 13,765 元和 14,345 元，看不出差別 |
| 判斷表 | 由上往下，符合就停：滿意 ≥ 75% → +1；滿意 ≥ 60% → +0.5；滿意 < 15% 或不滿 ≥ 40% → −1；滿意 < 30% 或不滿 ≥ 25% → −0.5；沒有人進店 → 不變；其他 → 不變 |
| 驗收 | 口碑規則 4／11 → 11／11；`playtest` 案例 T4 |
| 教學重點 | 把規則書的整張表格貼給 AI，請它照表實作；練習「給 AI 清楚的規格」 |
| 補充 | 客人的預算檢查**本來就是對的**：多數客人預算夠高（例如上班族 100 元）買得起最高價，只有窮學生（60 元）買不起 90 元的招牌。這不是 bug |

### bug 4：每日任務規則（永遠施工中）

| 項目 | 內容 |
|---|---|
| 檔案 | `web-lab/src/game/rules/tasks.js`，函式 `checkTask` |
| 規則書 | 「每日任務與結算」：第 1 天零報廢（獎金 100）、第 2 天沒有客人因為賣完而沒買到（150）、第 3 天賣出 30 份以上鍋貼（150）、第 4 天星等達到 4 顆（150）、第 5 天淨利 800 元以上（200） |
| 掉漆版 | 永遠回傳 `'wip'`（施工中），永遠不發獎金 |
| 學生看到的怪事 | 打烊報表的任務欄永遠寫「施工中」 |
| 怎麼發現 | 「任務欄寫什麼？」「我明明零報廢，怎麼沒拿到 100 元？」 |
| 修好後 | 依當天任務顯示「達成」或「未達成」，達成就發獎金 |
| 驗收 | 每日任務規則 0／10 → 10／10；`playtest` 案例 T5 |
| 教學重點 | 檔案開頭的註解已經列出能用的資料欄位（`report.wasteTotal`、`report.visits`、`report.sold`、`report.starsAfter`、`report.profit`）；練習「讀註解、告訴 AI 去哪裡找資料」 |
| 連鎖影響 | 第 2 天和第 4 天的任務要靠 bug 1、bug 3 修好才判得準 |

### bug 5：說話規則（客人不說話）

| 項目 | 內容 |
|---|---|
| 檔案 | `web-lab/src/game/rules/speech.js`，函式 `pickLine` |
| 規則書 | 每位客人在五種情況會說不同的話：買到了、討厭的菜有上架所以沒進門、想吃的沒上架、賣完了、太貴了 |
| 掉漆版 | 永遠回傳 `null`，畫面上沒有泡泡 |
| 學生看到的怪事 | 客人默默進來、默默離開；官方客人包明明每個人都有寫台詞 |
| 怎麼發現 | 「客人有說話嗎？」「客人包裡有台詞嗎？台詞存在哪個欄位？」 |
| 修好後 | 每張客人卡片下面出現對應的台詞泡泡 |
| 驗收 | 說話規則 0／5 → 5／5；`playtest` 案例 T6 |
| 正確寫法 | `return customer.lines?.[outcome] ?? null;` |
| 教學重點 | 最簡單的一條，適合讓學生獨立完成、建立信心；也是後面自己寫客人包時「台詞會出現在哪裡」的伏筆 |

### bug 6：倉庫盤點規則（全綠的盤點表）

| 項目 | 內容 |
|---|---|
| 檔案 | `web-lab/src/game/rules/inventory.js`，函式 `checkDish`、`suggestQty` |
| 規則書 | 「倉庫盤點」：每天打烊後盤點每樣上架的菜，顯示在上方選單的「倉庫盤點」頁 |
| 盤點欄位 | 備貨、賣出、報廢、賣完後沒買到、狀態、明天建議備貨 |
| 狀態規則 | 賣完後有人沒買到 → 缺貨；報廢 5 份以上 → 報廢過多；其他 → 正常 |
| 建議備貨 | 賣出 ＋ 賣完後沒買到（也就是「今天真正想買的人數」） |
| 掉漆版 | 狀態永遠「正常」、建議備貨永遠 0 |
| 學生看到的怪事 | 預設路人、只上架招牌 5 份：盤點頁寫「正常」、建議 0。如果 bug 1 也還沒修，還會看到「備貨 5、賣出 10」 |
| 怎麼發現 | 「有幾位客人卡片寫『賣完了』？盤點頁怎麼寫？」 |
| 修好後 | 賣出 5、賣完後沒買到 5、狀態「缺貨」（紅色）、明天建議備貨 10 |
| 驗收 | 倉庫盤點規則 4／9 → 9／9；`playtest` 案例 T7 |
| 正確寫法 | `checkDish`：`if (missed > 0) return 'out'; if (waste >= 5) return 'over'; return 'ok';`；`suggestQty`：`return sold + missed;` |
| 教學重點 | 修完之後馬上寫 `reorder-check` Skill（只讀不寫的 Skill，對照 `new-customers` 會寫檔）；第 3 天 AI 店長會用它決定下一版每樣菜備幾份 |
| 重要觀念 | **倉庫盤點只是報表，不影響現金、星等和分數。** 它的價值是「每個數字都能驗算」，給 Skill 和 Agent 一份可以抓錯的資料 |
| 好用的教學時刻 | ① 掉漆版全綠時，AI 讀盤點會說「沒有要補的」：AI 照資料回答沒錯，是資料錯了。② bug 1 沒修時出現「備 5 賣 10」：一個 bug 會讓另一份報表跟著錯。③ 老師示範的最高分策略每天也有缺貨：每天最多備 80 份，建議量只是參考 |

## 4. 看起來像 bug、其實不是的地方

寫簡報時請不要把這些當成 bug：

| 現象 | 為什麼不是 bug |
|---|---|
| 遊戲不會存檔，重新整理就回到第 1 天 | 刻意設計。每次打開都回到原樣，學生玩遊戲不會改到專案檔案，也比較好除錯 |
| AI 改完程式、畫面自動更新時，遊戲可能重來 | 同上，正常現象 |
| 跳關時資金一律 1,000 元、星等一律 3 顆 | 規則書明定，跳關成績不列入排行 |
| 窮學生買不起 90 元的招牌鍋貼 | 預算檢查本來就是對的 |
| 倉庫盤點不影響分數 | 規則書明定它只是報表 |
| 老師示範策略也有缺貨 | 每天最多備 80 份，要把份數留給利潤高的菜 |
| 星等是 0.5 顆為單位 | 規則書明定 |
