# 規格撰寫

## 什麼時候用

需求只有一句話、還不能直接動手的時候。例如：「我想做升級商店」。

## 步驟

1. **先問，不要猜**：一次最多問 3 個問題，例如「可以買什麼？多少錢？效果持續多久？」
2. **對照現有規則**：讀規則書和 `web-lab/src/game/config.js`，指出新功能會碰到哪些既有規則
3. **寫成規格書**，存到 `docs/specs/<功能名稱>.md`，格式如下
4. 使用者確認規格書後，才交給 `change-feature` 流程實作

## 規格書格式

```markdown
# <功能名稱>

## 一句話說明
## 玩家可以做什麼（操作）
## 規則（用數字寫清楚，不要寫「適量」「一些」）
## 不做什麼（範圍外）
## 會影響到的既有規則
## 驗收案例（至少 3 個：輸入 → 預期結果）
## 要新增或修改的檔案
```

## 原則

- 每條規則都要能被驗收：寫得出「輸入什麼 → 應該看到什麼」
- 範圍越小越好：第一版只做最核心的一件事
- 不准修改老師檔（見 AGENTS.md）；需要改老師檔時，在規格書裡寫出來請老師決定
